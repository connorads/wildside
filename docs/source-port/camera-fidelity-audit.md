# Camera & Scroll Fidelity Audit

Adversarially-verified per-unit audit of the Kid Chameleon source-port camera and scroll subsystem. The core X/Y follow mathematics (`sub_71E4` target clamp, ±1 edge nudges, `(target-camera+4)>>3` smooth step clamped to ±8, the post-velocity defensive re-clamp, and the page-snap level seed) are faithful and reachable on the live path. The dominant failure pattern is instead a cluster of unmodelled *accumulator and clamp interactions at the edges of the camera routine*: the `$FFFFFB58` look-down accumulator still has a missing `loc_728C` floor-clamp decrement and a one-frame reference-Y timing skew, the forward MurderWall path drops its `loc_7334` `Camera_max_X_pos` right-bound clamp so the camera scrolls past the level's rightmost column, and two call-site/respawn details deviate (an unwired attach-frame follow and an invented +2px respawn carry). All but one of these are currently masked from players by the separately-tracked `.min(30)` cap that makes the whole down-look pan inert, so most surface only to a frame-exact TAS — but they are genuine spec mismatches that would become observable once that cap is lifted.

### Medium severity

**`loc_7334` `Camera_max_X_pos` right-bound wall clamp is absent from the live `step_murder_wall`** (`loc_7334` / `loc_7316` / `loc_7346`)
In the ROM, after the forward MurderWall advances (`add.l d7,(MurderWall_X_pos).w`), `loc_7334` clamps the wall's pixel X to `Camera_max_X_pos` (= level width in pixels − `$140`, the rightmost camera column): `move.w (Camera_max_X_pos).w,d0; cmp.w (MurderWall_X_pos).w,d0; bgt.s loc_7346; move.w d0,(MurderWall_X_pos).w` (kid.asm:7464-7468). The native forward branch does `wall.x_pos += speed`, computes the `$80`/`$100` gap threshold, then calls `forward_murder_wall_camera_push_loc_7346` without ever applying the `Camera_max_X_pos` clamp — `MurderWallState` carries no level-width/`Camera_max_X` field and `step_murder_wall` is never passed one, so the clamp exists only as a doc-comment quote (weather.rs:2275-2278) and is never executed. Near a forward MurderWall level's right edge (e.g. Hills of the Warrior 1, level `0x08`, also the `$100`-gap special case), native `wall.x_pos` accelerates unbounded past `Camera_max_X_pos`; the `loc_7364` snap in the forward push helper then writes `Camera_X_pos = MurderWall_X_pos`. Camera follow runs at lib.rs:3240/3588 (clamping the camera to `[0, width−$140]`) *before* `resolve_frame_hazards` calls `step_murder_wall` at combat.rs:10970, and the frame ends with no camera re-clamp, so the wall step's out-of-bounds write persists — a player/TAS-observable positional scroll-past the level's rightmost column at level end. The reverse path's own floor-clamp-to-0 is correctly ported. Severity is medium rather than high because the consequence is a bounded camera/positional scroll-past at level end (Kid is already at the kill line by then), not a wrong death or lifecycle outcome. No `// DEVIATION`/`// ORIGINAL_QUIRK` marker; the regression test `loc_7334_forward_wall_position_advances_by_speed` (combat_tests.rs:15749) quotes the clamp in its doc-comment but pins only the un-clamped `wall.x_pos == initial_x + speed`. Kind: missing. `crates/kid-core/src/weather.rs:2306-2323`, `crates/kid-core/src/weather.rs:2275-2278`, `crates/kid-core/src/types.rs:2645-2654`, `crates/kid-core/src/combat.rs:10970`.

### Low severity

**Look-down increment not gated on `KidGrabbedByHand` (native increments the accumulator while a Hand grabs Kid)** (`loc_7772` / `loc_8C12` / `loc_8CB6`)
Fixed 2026-06-13: the merged native look-offset branch now keeps Down-held as a no-decay case, but only applies the `addq.w #1` equivalent while `kid_grabbed_by_hand` is false. Regression: `loc_8c70_grabbed_kid_down_held_freezes_look_offset`.

**`loc_726C` reference (`$FFFFFA2E`) stored from pre-physics Y, but the ROM stores post-collision Y** (`loc_726C` / `loc_75D4` / `loc_8218` / `loc_8BF0` / `sub_71E4`)
The `loc_726C` ceiling pull-back compares Kid's current Y against `$FFFFFA2E` (last_kid_y). In the ROM, `$FFFFFA2E` is written at `loc_75D4`/crawl `loc_8218`/walk `loc_8BF0` from `y_pos(a3)` *after* `Character_CheckCollision` — the post-collision Y at the end of the movement step (walk `loc_8BF0` kid.asm:10046-10048; crawl `loc_8218` kid.asm:9002-9004; standing `loc_75D4` kid.asm:7712-7714). The native stores `camera_last_kid_y` (lib.rs:3160) from the pre-physics `kid_y` captured at the start of the look-offset block (lib.rs:3141), and reads it again next frame. Because position carries over between frames, the ROM effectively compares this-frame pre-physics Y against last-frame post-collision Y, whereas native compares it against last-frame pre-physics Y; the two references differ by one frame's physics+collision delta, so the `-2` pull-back's trigger condition (`kid_y < last_kid_y`) fires under different conditions than the ROM. Currently not player-observable because the separate `.min(30)` cap makes the look-down shift always 0, so an extra/absent `-2` only changes how fast `y_look_offset` settles toward 0 with no visible camera movement; observable if the cap were removed. Kind: deviating. `crates/kid-core/src/lib.rs:3140-3161`, `crates/kid-core/src/physics.rs:974-980`.

**`loc_728C` look-down accumulator decrement at the floor clamp is not modelled** (`loc_728C` / `loc_72A8`)
The Y-axis camera-follow has a third look-down accumulator mutation that bleeds the offset off once it has already pushed the camera target into the bottom (floor) clamp. ASM `loc_728C`: when `y_look_offset` (`$FFFFFB58`) `>= $1E` it adds the offset to the Y target, subtracts `$1E`, and if the result reaches `d1` (= level height in pixels − `$E0`, the floor max) it caps the target at `d1` *and* does `subi.w #1,($FFFFFB58).w` (kid.asm:7391-7399, with `d1` set at kid.asm:7365-7366). The native models the `loc_726C` (`-2`) and `loc_727E` (`-1`) decrements (lib.rs:3147/3152) and the offset addition+cap (movement.rs:7123-7125 plus `update_camera_axis` `.min(max_pos)` at physics.rs:927), but never decrements `y_look_offset` when the offset-extended target hits the bottom clamp. Consequence: holding Down at the bottom of a level leaves the native accumulator 1-per-frame higher than the ROM, so the look-down offset takes longer to decay and camera Y diverges for several frames after Kid moves away from the floor. Low magnitude / look-offset polish, but a genuine floor-clamp interaction a TAS would observe, not covered by any prior audit or backlog item. Kind: missing. `crates/kid-core/src/movement.rs:7117-7139`, `crates/kid-core/src/physics.rs:894-928`, `crates/kid-core/src/lib.rs:3140-3161`, `crates/kid-core/src/lib.rs:3609-3613`.

**Iron Knight wall-climb ATTACH frame skips `update_camera_follow` (`loc_A28A bsr sub_71E4` unwired)** (`loc_A276` / `loc_A28A` / `sub_71E4`)
When Iron Knight presses C against a wall and attaches, the native `AttachHibernate` branch sets velocities, clears `on_ground`, and returns without ever calling `update_camera_follow` (lib.rs:3192-3214). In the ASM the attach entry `loc_A276` falls into `loc_A28A`, which does `move.w #MoveID_Wall_Climbing,(Character_Movement).w; clr.w (Addr_PlatformStandingOn).w; bsr.w sub_71E4; jsr (j_Hibernate_Object_1Frame).w` (kid.asm:12580-12583) — advancing the camera one smooth-step on the attach/hibernate frame even though the player position is held. This is asymmetric with the sibling `ExitHibernate` branch, which the port correctly wires to `update_camera_follow` at lib.rs:3240 (its comment even notes "loc_A6F8 still runs sub_71E4, so camera follow advances once on the hibernated release frame"); the `ResumeClimb` branch (movement.rs:4945) also calls it. Only the first attach frame omits it. Consequence is one frame (up to ±8px) of camera scroll lag, deterministic and TAS-observable, with no effect on player physics/collision. The `// ORIGINAL_QUIRK` comment at lib.rs:3193 concerns position preservation during hibernate, not camera, so this omission is not a documented deviation. Kind: missing. `crates/kid-core/src/lib.rs:3192-3214`, `crates/kid-core/src/helmets.rs:5418`, `crates/kid-core/src/movement.rs:7117`.

**Respawn camera +2px Y carry is an invented per-frame substitute, gated by residue value not by level or ASM trajectory** (`sub_71E4` / `loc_71EC` / `loc_726C` / `loc_727E` / `loc_728C` / `loc_72A8` / `loc_72C8` / `loc_72E2` / `Load_InGame (loc_11F48 camera seed)` / `lose_life` / `Teleport` / `loc_B8DE` / `loc_6E2`)
`finish_respawn_camera_convergence` (level.rs:18786-18801) fabricates a final camera beat by re-running `update_camera_axis` with `player_y+2` whenever the settle loop leaves the camera exactly 2px above the plain target (`target_y - camera_y == 2`) and grounded, nudging camera +1px. The ROM has no hidden `sub_71E4` settle loop: `Load_InGame` seeds the camera once by page-snap (`divu.w #$140`/`divu.w #$E0`, floor to screen cell) then returns (kid.asm:24132-24145, ending `move.l d0,(Camera_Y_pos).w` then `rts`); `sub_71E4` only runs on real, player-controlled gameplay frames. A genuine extra `sub_71E4` beat at delta=2 produces velocity `(2+4)>>3 = 0` — it does nothing; the entire +1px effect comes from the invented +2 player-Y shift, which has no ASM counterpart (the "carrying a final +2px pre-settle Y target" comment is inferred from oracle traces, not the disassembly). The carry is gated on residue value (`delta==2`), not on level `0x24`/`0x51` (lib check absent at level.rs:18789-18798), so any other level — including cases the ROM itself leaves at delta=2 — gets an unjustified +1px down nudge. Root cause: the native floor-snap-then-gravity-replay approximation reaches a different camera fixed point than the ROM's frame-by-frame fall for these two levels, and the carry is a band-aid over that trajectory divergence. Consequence is purely a 1px camera-Y at the respawn settle frame, observable only to a frame-exact TAS respawn comparison; it currently yields the correct oracle values for `0x24`/`0x51` per backlog #037. No `// DEVIATION` marker, so it is presented as faithful. Kind: deviating. `crates/kid-core/src/level.rs:18782-18802`, `crates/kid-core/src/level.rs:18765`, `crates/kid-core/src/level.rs:17932`, `crates/kid-core/src/physics.rs:894-928`.

Units with ambiguity or theoretical-only notes (not flagged as gaps):

- **Final post-velocity `.max(0).min(max_pos)` re-clamp on both axes** (physics.rs:925-927) — proven a no-op over the reachable state space (target pre-clamped to `[0,max_pos]`; edge nudges only move toward an in-bounds bound; smooth step clamped to ±8 toward an in-bounds target), and acknowledged in-code as a defensive guard. Not an invented saturation.
- **X-axis target upper-clamp signedness** (`loc_720E` unsigned `bcs.s` vs native signed `.min()`) — diverges only if `max_pos < 0` (level width below `$140` / one screen), which is never reachable since width is always ≥1 screen. Theoretical-only.
- **Look-offset add-before-vs-after the floor-at-0 clamp** (native adds offset before flooring `kid_y−$A0` to 0; ASM floors first then adds) — diverges only if Kid is simultaneously near the level ceiling and holding Down (`offset >= $1E`), which is not normally co-reachable; the ASM is effectively unambiguous and was not flagged. Would warrant an oracle probe only if that co-reachable state is demonstrated.
- **Respawn settle "hidden frames" abstraction** — the ROM `Load_InGame` page-snaps the camera once with no hidden `sub_71E4` settle loop; the native settle construct is a port-specific approximation of where the camera would land after N real gameplay frames. The trajectory divergence underlying the +2px carry (#038) is the root cause and would benefit from an oracle probe of the real frame-by-frame fall for levels `0x24`/`0x51`.
