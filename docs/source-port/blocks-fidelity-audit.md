# Block Lifecycle & Interaction Fidelity Audit

Adversarially-verified per-unit audit of the Kid Chameleon source-port block subsystem. The dominant failure pattern is the same one that recurs across the codebase: ASM-faithful pure helpers exist and are unit-tested but carry `#[cfg_attr(not(test), allow(dead_code))]` and are never wired into the live step path, so the runtime falls back on an invented substitute. Here that pattern manifests three ways — (1) entire dispatch arms silently dropped (no `BlockType::Ice` arm on the shared `off_BB80` ceiling headbutt; the immediate telepad warp shadowing the 90-frame `loc_B522` countdown), (2) the correct helper present but fed a hardcoded or wrong selector value (smash-debris direction, ice-bullet direction, metal-bounce arc), and (3) gating logic computed against the wrong counter (rubber jiggle budget capped against global `Number_Objects` rather than the dedicated `$FFFFFB5A` rubber-worker count). Several of these are confined to revisit/edge paths, but three high-severity gaps — Ice ceiling headbutt, Red-Stealth ice bullets, and immediate telepad warp — are reachable in ordinary play.

For a type-7 block whose skin differs from `$10` (e.g. a hidden-block reveal `cell_word = 0xE710 + block_setting`, or a directly-placed custom skin), the moved block renders with the wrong terrain graphic. Collision is unaffected (collision/type nibbles are identical). Severity is low pending confirmation a shipped level places such a block. Distinct from the #68 swap-timing item. Kind: deviating. `crates/kid-core/src/blocks.rs:3352`, `crates/kid-core/src/blocks.rs:3353`, `crates/kid-core/src/blocks.rs:3479`.

**`sub_F096` visibility scan registers type-8 Shooter cells that the ROM scan rejects (only type-`$C` accepted)** (`loc_F106` / `loc_F1DE`)
ASM `loc_F106` accepts a shooter candidate only when the block-type nibble is `$C` (Drill): `andi.w #$F00,d6; cmpi.w #$C00,d6; bne`. The direction bitfield is always `(word & $FF) - $2D`. Native `shooter_direction_bits_loc_F106` adds an extra acceptance branch for `BlockType::Shooter` (type-8), returning the raw skin as the direction bits (no `-$2D`), so a type-8 cell would be registered with the wrong direction decode. No shipped level contains any type-8 cell (0 found vs 864 type-C and 562 type-9), so this is a latent deviation with no current observable effect but a genuine spec mismatch for custom/hacked levels. Kind: deviating. `crates/kid-core/src/blocks.rs:508`, `crates/kid-core/src/blocks.rs:518`.

**Headbutt dispatch routes type-8 Shooter blocks to the destroy-worker; ROM `off_BB80[8]` is a no-op (`rts`)** (`off_BB80` / `loc_BBC2` / `return_1142E` / `loc_11430`)
The ROM `off_BB80` dispatches index 8 (Shooter) to `j_return_1142E` (a bare `rts`) — headbutting a type-8 block does nothing — while index 9 (Mushroom) dispatches to `loc_BBC2` → `loc_11430`. Native matches `BlockType::Shooter | BlockType::Mushroom` together and sets `shooter_block_hit` for both, so a headbutted type-8 block would be deleted and run the center/support worker. No shipped level uses type-8 (0 cells), so no current observable effect; the type-9 routing itself is faithful. (See the scout note: removing the combined arm breaks 18 tests under the established multi-source `BlockType::Shooter` convention from #250, so a fix needs an oracle probe of a real type-8 ceiling headbutt.) Kind: deviating. `crates/kid-core/src/movement.rs:6428`.

**Dead `drill_projectile_hit` consumer invents direction from player x-position; real drill firing is faithful via the shooter scan** (`loc_F106` / `sub_F096` / `sub_1129C`)
The block-effect path consumes `slice.drill_projectile_hit` and spawns a horizontal `EnemyProjectile` whose direction is invented from `slice.player.x_pos >= x_fp`, with a comment misattributing the effect to `sub_1129C` (which is actually the Berzerker metal-block push worker). `drill_projectile_hit` is never assigned `Some(...)` in production, so this consumer is unreachable dead code. The actual drill-block (type `$C`) projectile firing is handled faithfully by `step_shooter_blocks` via `shooter_direction_bits_loc_F106`, reading direction from the block setting byte as `skin - $2D` and firing per-direction bullets. Low: dead/redundant code with a wrong ASM citation, no observable effect (#064 drill-projectile-horizontal is already closed). Kind: helper-unwired. `crates/kid-core/src/blocks.rs:3644-3657`, `crates/kid-core/src/types.rs:2665`, `crates/kid-core/src/lib.rs:2888`.

**Telepad destination lookup keyed by feet/contact cell `(col,row)` instead of the `$FFFFFA86` telepad layout address (and its `-2` adjacent)** (`loc_BC80` / `loc_BC96` / `loc_BCB2`)
`loc_BC80` matches the destination by the stored telepad layout address in `$FFFFFA86` *and* `d6-2` (the adjacent cell) against each entry's layout word. Native `teleporter_at` matches by `(col,row)`: the `blocks.rs` path keys on the contacted cell, and combat's `check_teleporter_contact` keys on the player's feet cell (`pixel_to_cell`), neither of which uses the layout-address or the `-2` adjacency. The ASM also accepts `layout_addr-2` (the cell to the left), which native does not model, and combat keys on whichever cell the feet pixel rounds to. Low because in normal single-cell play the contacted cell equals the telepad cell. Kind: deviating. `crates/kid-core/src/terrain.rs:843`, `crates/kid-core/src/combat.rs:9008`, `crates/kid-core/src/blocks.rs:3662`.

**Two independent live teleporter warp implementations fire in the same frame** (`loc_BC80` / `Teleport`)
The single ASM teleport path (`loc_BC80` → `Teleport`) is duplicated in native by two consumers that both run each frame: `process_block_effects` (always an inline same-level reposition keyed on `teleporter_contact`) and `resolve_frame_hazards` (cross-level `pending_level_skip` *or* inline reposition keyed on the feet cell). `lib.rs` runs both in the same step, so on a contact frame both can act on the player. They use different dest scaling (`dest_x*16<<16` vs `dest_x<<20`, numerically equal) and different cross-level handling (`blocks.rs` ignores `dest_map_id` entirely), risking the inline `blocks.rs` warp masking the cross-level skip the combat path intends. Kind: deviating. `crates/kid-core/src/blocks.rs:3660`, `crates/kid-core/src/combat.rs:10949`, `crates/kid-core/src/lib.rs:3755`, `crates/kid-core/src/lib.rs:3763`.

**`step_ghost_blocks` omits the ~8-frame reveal/vanish animation latency of the `sub_F730` ladder** (`sub_F730` / `loc_F8A6` / `loc_F78C` / `loc_F7AA`)
The `sub_F730` ladder keeps a SolidGhost block visibly solid through `0`→`$8001`→`$8002`→state3→`$8004`→`$8005` (roughly the reload hold plus 8 animation frames) before the clear, then holds the vanished phase for the other reload value. Native `step_ghost_blocks` toggles instantly each timer expiry with no per-step animation frames, so the solid/vanish boundaries land several frames early. There is also an unresolved ambiguity about which reload field maps to the solid hold (ASM solid from `6(a0)`, vanished from `4(a0)`), depending on a level-loading record interpretation outside this unit's scope. The low-severity animation-latency corollary of the medium SolidGhost helper-unwired gap above. Kind: deviating. `crates/kid-core/src/blocks.rs:2639`.
