# Scoring & Prize-Economy Fidelity Audit

Adversarially-verified per-unit audit of the Kid Chameleon source-port scoring and prize-economy subsystem. The dominant failure pattern is the recurring source-port disease: ASM-faithful pure helpers exist and are unit-tested but carry `#[allow(dead_code)]` / `#[cfg_attr(not(test), allow(dead_code))]` and are never wired into the live frame step, so the runtime either does nothing or falls back on an invented substitute. The starkest instance is the entire Hundred-K-Trip mechanic: the native arms the 60-frame timer in normal level-4 play, then never decrements it and never reaches the faithful-but-dead warp-body helper chain — an authoritative level-flow event that is wholly absent. The second recurring shape is a wrong constant pinned by a regression test: `add_life` caps lives at 9 (the ROM caps at 99, and only at HUD-render time), while the clock-prize 180s vs 181s constant is now fixed-candidate. Audio cues fare no better: the Continue/coin pickup plays no `sfx_Coin_prize`.

## Confirmed gaps

### High severity

**Hundred-K-Trip 60-frame timer (`$FFFFFB4C`) is armed but never decremented per frame, so the warp never triggers** (`loc_7452` / `loc_10AC2` / `loc_D980`)
ASM main-loop `loc_7452` (kid.asm:7586-7591) runs every in-game frame: after `Hibernate_Object_1Frame` it does `tst.w ($FFFFFB4C).w; beq.s loc_7464; subq.w #1,($FFFFFB4C).w; beq.w loc_D980` — a nonzero timer is decremented each frame and, on reaching zero, control jumps to the `loc_D980` warp body. The arm site `loc_10AC2` (kid.asm:22378-22382) seeds the timer to `$3C` (60) when Score>=100000 on `HundredKTripStart_LevelID` (4) with the timer clear. Native arms `hundred_k_trip_timer` faithfully in `arm_hundred_k_trip_timer_loc_10_ac2` (combat.rs:8649, live-reachable from `add_score` via the collect-diamond/Prize10000/generic-score paths), so the timer genuinely reaches `0x3C` in real level-4 play — but a crate-wide grep shows the field is only ever assigned 0 (lib.rs:1412 init; boot.rs:5947/5989/7525 resets) or set to `0x3C` in the arm helper, and read once in the arm guard (combat.rs:8660). It is never decremented, never compared to 1, and `step_frame` (lib.rs:1925) contains no reference to it. The armed timer is therefore inert forever and the level-completion warp can never fire. Kind: missing. `crates/kid-core/src/lib.rs:316`, `crates/kid-core/src/lib.rs:1925`, `crates/kid-core/src/combat.rs:8649`.

**Hundred-K-Trip warp body (`loc_D980` → `loc_DA4A` teleport, Score=1000001) is implemented as dead test-only helpers with no production caller** (`loc_D980` / `loc_D99E` / `loc_D9EA` / `loc_DA16` / `loc_DA30` / `loc_DA4A`)
The ASM warp body reached from `loc_7452` at timer-zero (`loc_D980`..`loc_DA4A`, kid.asm:17007-17092) clears object-collision longwords on every non-current object, runs `Delete_AllButCurrentObject`, performs a palette fade (`loc_DA16`/`loc_DA30`), then at `loc_DA4A` (kid.asm:17083) does `move.l #1000001,(Score).w; move.w #$20,(PlayerStart_X); move.w #$48F,(PlayerStart_Y); move.w #HundredKTripDest_LevelID,(Current_LevelID)` (=$1F); `clr.w (Current_Helmet); st ($FFFFFC29); bra.w Teleport`. Native models this entire chain as the `EndCreditsHundredKTrip*` helper family (`end_credits_hundred_k_trip_setup_loc_D9EA` level.rs:16329, `_palette_setup_loc_DA16`, `_fade_step_loc_DA30`, `_teleport_loc_DA4A` level.rs:16433, plus the `loc_D984` clear at level.rs:16251 and `_tile_upload_loc_DA7A` at level.rs:17447). Every member is `#[allow(dead_code)]` and a per-name grep shows each is referenced only from `tests/level_tests.rs` — zero production callers. The teleport helper's constants match the ASM exactly (score 1_000_001, x 0x20, y 0x48F, level 0x1F, helmet 0, continue-latch true, tail "Teleport"), so the helpers are faithful but completely unwired; even if a decrement were added there would be no live warp execution. Kind: helper-unwired. `crates/kid-core/src/level.rs:16329`, `crates/kid-core/src/level.rs:16379`, `crates/kid-core/src/level.rs:16433`, `crates/kid-core/src/level.rs:16251`.

These two gaps are coupled (one missing-decrement, one unwired warp-body) but distinct kinds; together they mean the Hundred-K-Trip mechanic — timer countdown → object teardown → score sentinel → level swap to $1F → teleport — produces zero live effect despite the arm being reachable. Reachability in normal play requires reaching 100000 points while on level 4 with the timer clear, an attainable but specialised condition; this does not lower the severity since the behaviour is fully absent when the condition is met. The only adjacent prior-doc entry is `level-loading-fidelity-audit.md:211-212`, which tracks a *different* facet (the EOL flagpole path spuriously calling the arm helper) and does not address the never-decremented timer or the never-firing warp body.

### Medium severity

**`add_life` caps lives at 9, but the ROM has no per-award cap — its only ceiling is the 99-life HUD display clamp (`loc_BF2A`)** (`PrizeAnkhCollected_Init` / `Prize10000Points_Init` / `loc_10AAE` / `loc_BF2A` / `life_display`)
The native `add_life()` (combat.rs:8626-8630) refuses to increment once `number_lives` reaches 9 (`if self.progression.number_lives < 9`), with a doc-comment "capped at 9 per ASM" that the disassembly does not support. Every ASM life-award site is a bare `addq.w #1,(Number_Lives).w` with NO per-award cap: the Ankh award `PrizeAnkhCollected_Init` (kid.asm:21228), the Prize10000 50K-boundary award `loc_10AAE` (kid.asm:22373), the alternate score-boundary award (kid.asm:16877), and the Diamond-Power extra-life (kid.asm:44975). The ONLY lives clamp in the ROM is the per-frame HUD routine `loc_BF2A` (kid.asm:15527-15531): `cmpi.w #100,d0; blt.s life_display; moveq #99,d0; move.w d0,(Number_Lives).w` — the true ceiling is 99, applied once at render time, not 9 at award time. `number_lives` is `u16`, so 10..99 are representable. `add_life` is reachable on the live frame path from `apply_prize_content` (the Ankh arm at combat.rs:8806) and from `add_score`'s 50K-boundary loop, so a player at 9 lives who collects an Ankh — or crosses a 50,000-point boundary — gains nothing in native where the ROM would keep counting to 99. The faithful 99-clamp helper `hud_lives_clamp_loc_BF2A` (boot.rs:730) is itself dead (referenced only from `tests.rs:28` and `boot_tests.rs`), so neither ceiling is applied live. Regression tests `add_life_caps_at_nine` (level_tests.rs:17192), `lives_capped_at_nine` (combat_tests.rs:6068) pin the invented value with no ASM citation. Reported independently by three units (ten-thousand-point-prize, ankh-extra-life-prize, prize-value-dispatch-table); merged here. Kind: deviating. No `// DEVIATION`/`// ORIGINAL_QUIRK` marker. `crates/kid-core/src/combat.rs:8626`, `crates/kid-core/src/combat.rs:8806`, `crates/kid-core/src/blocks.rs:3809`, `crates/kid-core/src/boot.rs:730`.

**RESOLVED candidate — clock prize applies the ASM +1 second before the +3 minutes (and cap carry)** (`PrizeClockCollected_Init` / `loc_FFDE` / `loc_FFFC` / `loc_10002`)
ASM `PrizeClockCollected_Init` runs an explicit one-second BCD increment of the level timer (`Time_Seconds_low_digit` +1, with carry into the tens digit at `#$A` and into `Time_Minutes` at `#6`, kid.asm:21271-21279) immediately before reading `Time_Minutes` and adding 3 minutes at `loc_FFDE` (kid.asm:21282-21288). Native `add_clock_bonus` now adds `LEVEL_TIMER_CLOCK_COLLECT_SECONDS=181`, caps to 10:00, and still resets `sub_frames` to 1 for `loc_FFFC`; the next countdown tick cancels that extra second so the live display nets a clean +3:00. The `clocks_collected` increment and speed-bonus elapsed-time formula remain on flat `$B4` via `LEVEL_TIMER_CLOCK_BONUS_SECONDS`, matching `loc_C10A`. Regression tests cover the post-tick clean +3:00 and the 6:59→10:00 cap boundary. Kind: fixed-candidate. `crates/kid-core/src/types.rs`, `crates/kid-core/src/combat.rs`, `crates/kid-core/src/trace.rs`, `crates/kid-core/src/constants.rs`.

**RESOLVED candidate — Continue-prize pickup plays `sfx_Coin_prize` (`$2C`) on the increment frame** (`CharacterCollision_TouchCoin` / `CharacterCollision_TouchNonHelmetPrize` / `CharacterCollision_TouchSpecialPrize` / `Character_CheckCollision`)
When the Kid touches a Continue/coin prize object (`object_meta $98` set by `PrizeContinue_Init`, kid.asm:22040), `Character_CheckCollision` routes `object_meta>=$64` through `TouchPrize` -> `TouchSpecialPrize` -> (d5>=$90) `TouchNonHelmetPrize` -> table index 2 -> `CharacterCollision_TouchCoin` (kid.asm:14903-14910), which does `addq.w #1,(Number_Continues).w` and plays `sfx_Coin_prize` (=$2C per constants.asm:37) via `j_PlaySound`. Native now pushes `QueuedSoundEffect::CoinPrize` from the live `PrizeContent::Continue` arm immediately before incrementing `number_continues`, distinct from the separate `$6A` sound the prize-block object plays on delete in `PrizeContinue_Init loc_10838`. Regression `prize_content_continue_queues_coin_sound_on_increment_loc_b952` pins the counter increment and `$2C` cue together. Kind: fixed-candidate. `crates/kid-core/src/combat.rs`, `crates/kid-core/src/tests/combat_tests.rs`.

### Low severity

**`add_score` awards one life per crossed 50K boundary via a loop; ASM does a single `addq` on a divu-quotient change** (`loc_10AAE` / `Prize10000Points_Init`)
The ROM compares `divu.w #50000` quotients of the pre-add score (d0) and post-clamp score (d1) and issues a SINGLE `addq.w #1,(Number_Lives).w` only when they differ (kid.asm:22369-22373). Native `add_score` instead computes `old_lives = old_score / 50000` and `new_lives = …` and loops `for _ in old_lives..new_lives { add_life() }` (combat.rs:8641-8644), awarding one life per boundary crossed. Currently NOT observable: every live `add_score` caller passes <=50,000 (collect_diamond 500, Points10000 10000, and EOL bonuses each <=50000), so a single call can cross at most one boundary and the loop awards at most one life. The sibling EOL helper `eol_score_counter_awards_life_loc_D79E` (level.rs:17580) correctly models the single-life-on-quotient-change semantics, so `add_score` is the structurally divergent one — but no live caller can trigger >1 life. Kind: deviating. `crates/kid-core/src/combat.rs:8633`.

**The `blocks-fidelity-audit.md` "dead mechanic" claim for the Continue counter is contradicted by the ASM; the native increment is authoritative and the backlogged no-op "fix" would regress it** (`CharacterCollision_TouchCoin` / `Continue_Screen` / `Use_Continue`)
`blocks-fidelity-audit.md:90` states `Number_Continues` is "accessed nowhere in the disassembly — the Continue prize is a dead mechanic" and the native increment "has no in-game effect", and its backlog row (line 142) proposes making the Continue arm a no-op on the counter. That premise is wrong: `kid.asm` contains a high/NUL byte so plain `grep` treats it as binary and prints nothing, while `grep -a` reveals five live accesses — increment at `TouchCoin` (kid.asm:14905), and at the game-over Continue screen `tst.w (Number_Continues).w; bne.w Continue_Screen` (16473) gates whether a continue is offered, the value is displayed (16523), and `Use_Continue` (16563) does `subq.w #1` then resets `Number_Lives` to 3, clears helmet/diamonds and `Teleport`s (an authoritative level restart). Native already implements this authoritatively (`boot.rs:7764` gates the ContinueCountdown on `number_continues > 0`; `boot.rs:7786` decrements and resets lives to 3). The native increment is therefore correct and load-bearing; applying the backlogged no-op fix would break the continue economy. Flagged here so the stale prior-doc claim and stale native cite (`combat.rs:8769`, now `8802-8805`) are corrected, not actioned as a removal. Kind: deviating (documentation/regression-risk). `crates/kid-core/src/combat.rs:8802`, `crates/kid-core/src/boot.rs:7745`, `docs/source-port/blocks-fidelity-audit.md:89-90`, `docs/source-port/blocks-fidelity-audit.md:142`.
