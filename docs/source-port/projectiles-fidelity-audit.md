# Projectile System Fidelity Audit

Adversarially-verified audit of the player-form projectile and melee weapon paths in the Kid Chameleon source-port. The dominant failure pattern is the same one the enemy audit found, sharpened here onto player weapons: an ASM-faithful collision predicate exists in `terrain.rs` (`probe_relative_collision_sub_B55C`, the exact `& $7000 == $6000` gate) and is wired into live movement, yet every projectile terrain probe substitutes the generic `solid_terrain_at` (`collision != Empty`), so the Juggernaut skull bounces off slopes, spikes and hidden blocks it should fly through. Around this core recur two further motifs: invented per-projectile timers and gates with no ASM basis (120-frame DBF lifetimes on the Lion projectile and skull; the Maniaxe one-at-a-time gate keyed to projectile existence rather than the ~17-frame throw animation; the live Maniaxe axe being silently skipped for damage because it spawns with `lifetime: 0`), and invented hitboxes/behaviours (the Red Stealth below-foot airborne stomp the ROM never performs). Several faithful helpers — `hidden_block_column_updates_sub_E446`, the Lion owner-token cull helpers — sit dead beside the live path that does not call them.

## Confirmed gaps

### High severity

**Maniaxe axe never damages or is consumed by enemies in live play** (`loc_8ABC / loc_8A52 / loc_8AF2`)
Per ASM `loc_8ABC` (kid.asm:9902-9910) the thrown axe, on enemy contact, both damages the enemy (via its `collision_type`) and is unconditionally deleted (`jmp Delete_CurrentObject`). The live axe spawn (`step_maniaxe_axe`) creates the projectile with `lifetime: 0` and the projectile step exempts the axe from the `lifetime==0` despawn (projectiles.rs:2393), so its lifetime stays `0` for its whole life. But the sole live enemy-damage path, `process_friendly_projectile_hits` (called from combat.rs:10996), begins every iteration with `if !proj.friendly || proj.lifetime == 0 { continue; }` (helmets.rs:5879). The live axe always matches `lifetime==0` and is skipped: it never calls `take_colid_hurt_or_queue_death` and is never added to `projectile_consumed`. The `ManiaxeAxe` arm of `friendly_projectile_enemy_hit_extents` (helmets.rs:4319) is dead for live axes. Kind: deviating (regression introduced by backlog #236, which switched the axe to `lifetime=0` and updated the step/active-state checks but not this damage guard). The damage regression tests are masked because they manually push `lifetime: 20` (projectile_tests.rs:4159), while the spawn test pins `lifetime == 0`. Cited native: helmets.rs:5879, 6342; projectiles.rs:2393.

**Juggernaut skull bounces off spikes/slopes/hidden blocks; ASM only treats exactly-Solid ($6000) as wall** (`sub_87B0 / sub_B55C / loc_8852 / loc_8864 / loc_8890 / loc_8916 / loc_8958 / loc_8810`)
The ASM skull collision is gated by `sub_B55C` returning `d5 = tileword & $7000` followed by `cmpi.w #$6000,d5; beq` at every probe (kid.asm:9647-9649, 9679-9680, 9706-9707, 9758-9759, 9785-9786): the cell must be exactly collision-class `$6000` (Solid). Spikes (`$7000`), slopes (`$4000`/`$5000`) and hidden block (`$2000`) are not solid to the skull, which arcs through them. The live native path uses `Self::solid_terrain_at`, defined as `cell.has_block && cell.collision != CollisionKind::Empty` (terrain.rs:1674-1678 / projectiles.rs:1697-1702) — true for HiddenBlock, SlopeUp, SlopeDown, Solid and Spikes. The native skull spuriously wall-snaps and ¾-rebounds off four extra block classes it should ignore, changing trajectory, bounce-budget (`reaim_countdown`) consumption, and explosion location on common level geometry. Applies to both the x-axis (projectiles.rs:2014) and y-axis (projectiles.rs:2059) probes, on the live frame-step path (`step_projectiles` → `step_juggernaut_skull_sub_87B0`, projectiles.rs:2489-2490). Kind: deviating. Secondary divergence: `sub_B55C` masks off the `$8000` has-block bit, so the native extra `has_block` requirement is also absent from the ROM probe. The sibling Maniaxe axe path was already corrected to `== Solid` (projectiles.rs:861, loc_8A84) but the skull path was not migrated. (Merged: this single root deviation was independently reported by the `juggernaut-skull-shot-lifecycle`, `skull-terrain-probe-fidelity` and `projectile-vs-block-contact-and-prize-break` units; the latter two rated it medium, but the lifecycle auditor's verified reachability and budget/explosion impact place it high.)

**Live skull collision uses generic `solid_terrain_at` instead of the faithful `probe_relative_collision_sub_B55C` helper** (`sub_B55C / sub_87B0`)
The ASM-faithful equivalent of `sub_B55C` exists and is wired into live movement: `terrain::probe_relative_collision_sub_B55C` (terrain.rs:1665) returns the exact `CollisionKind` from `relative_collision_mask_loc_331D2(...) & 0x7000` and is called live in movement.rs (4537/7639/7985/8004/8087/8097) and helmets.rs:322. The Juggernaut skull's live step does not use it; it substitutes the generic `Self::solid_terrain_at` at projectiles.rs:2014/2059. Wiring the skull to `probe_relative_collision_sub_B55C(grid, x, y, 0, 0) == CollisionKind::Solid` restores the exact `==$6000` gate (and drops the spurious `has_block` requirement), fixing the high-severity pass-through deviation above. Kind: helper-unwired — the mechanical cause of the preceding gap. Cited native: terrain.rs:1665, projectiles.rs:2014, projectiles.rs:2059.

**Maniaxe one-at-a-time gate keyed to axe-object lifetime, not the ~17-frame throw animation** (`loc_76E4 / loc_8CB6 / loc_A7F8 / sub_78E8 loc_794C / loc_9454 / loc_B334`)
The ROM single-axe gate is the byte flag `Maniaxe_throwing_axe`: set on C-press (loc_76E4/loc_8CB6/loc_A7F8), and CLEARED every frame by the animation dispatcher `sub_78E8`/`loc_794C` (and `sub_942A`/`loc_9454`) the moment the Kid's throw animation finishes — gated only on the Kid's `$18(a3)` anim-done flag (kid.asm:7984-8010), NOT on the axe object. The throw animations `stru_8B4E` and `stru_8B60` are both 17 frames, so ~17 frames after a throw the player can throw a second axe while the first is still boomeranging (minimum out-and-back ≥24 frames), permitting multiple axes on screen. Native instead clears `maniaxe_axe_active` only when no `ManiaxeAxe` projectile remains (helmets.rs:6377-6383), and the axe has no DBF lifetime (excluded at projectiles.rs:2393), so it persists until it leaves the camera box or hits terrain/an enemy — forbidding a second throw for far longer than the ROM and capping the player at exactly one axe. Kind: deviating. The ROM-mirror field `helmet.maniaxe_throwing_axe` exists but is only fed to a RedStealth-gated helper that hardcodes it `false`, so the anim-based clear is unreachable for the Maniaxe form. Backlog #236 deliberately removed the DBF lifetime and keyed active-state off the axe object existing — which is precisely what introduced this gate-duration divergence — without addressing the throw-animation clear semantics. Cited native: helmets.rs:6328, 6377-6383; projectiles.rs:2385-2415.

**Invented below-foot airborne hitbox damages enemies the ROM never hits** (`loc_B350 / loc_B380 / sub_868E / loc_86CE / loc_76B0 / loc_8CF8`)
In the ROM, `sub_B270` `loc_B350`/`loc_B380` only writes `Red_Stealth_sword_swing` (`$FFFFFA6F`) to pick the down-slash SPRITE phase and play `sfx_Red_Stealth_attack_down`; it allocates NO hitbox object. The only Red Stealth damage source is the `sub_868E` sword worker, spawned solely on a C-press while the swing byte is `0` (loc_76B0:7781 / loc_8CF8:10126); it fixes its position ONCE at spawn to x = kid_x ±$1C (28px to the SIDE) and y = kid_y−$A (10px ABOVE the foot), never below. Native `process_sword_hits` instead builds an independent hitbox at `(kid_x, kid_foot_y + RED_STEALTH_AIRBORNE_SLASH_DOWN_REACH_PX = 12)` whenever `red_stealth_airborne_slash_counter > 0`, which `step_red_stealth_airborne_slash` sets every frame the player is RedStealth + airborne + descending + C held, independent of any sword-worker spawn. This grants a phantom below-foot stomp a player/TAS would observe (enemies dying from falling onto them with C held) that does not exist in the ROM. The native's own constants.rs:697-703 comment admits "The ROM doesn't allocate a separate hitbox GfxObject for this path"; tests at projectile_tests.rs:2410-2460 pin the deviating below-foot kill. Kind: deviating, live, player-observable. Cited native: helmets.rs:5807/5820/5823, constants.rs:703, lib.rs:3016, combat.rs:10995. (Already tracked — see below — but understated.)

### Medium severity

**Shared pump applies projectile gravity pre-move; ROM generic-mover projectiles add gravity post-move** (`loc_3263C / loc_325B6 / loc_338F8 / Hibernate_Object_1Frame`)
In the shared `retain_mut` pump, `p.y_velocity += p.gravity` runs at projectiles.rs:2435 BEFORE the position integration at 2721-2722, for every gravity-bearing projectile except DripsDrop. The ROM template for `is_moved` generic-mover projectiles (Tar/Drips burst glob: `loc_325B6` → `loc_3261C` sets `st is_moved`, then `loc_3263C` yields via `Hibernate_Object_1Frame`, the engine integrates velocity into position during the hibernating frame, and ONLY THEN `addi.l #$1000,y_vel`) adds gravity AFTER the move, preparing the next frame. So the burst children (`TarMonsterBurstChild` and `DripsSurfaceCrawlerBurst`, both gravity `0x1000`, generic move) get one extra gravity tick folded into their very first move, shifting the whole vertical trajectory by one gravity frame. The DripsDrop branch was special-cased to post-move gravity at 2727, proving the shared layer knows the correct order but applies it inconsistently. `Hibernate_Object_1Frame` (kid.asm:1690) is a coroutine yield, not a move, so the juggernaut skull's pre-move gravity is correct (it uses its own explicit mover `sub_87B0` with no `is_moved`); only the generic-mover `is_moved` projectiles are affected. Kind: deviating; TAS/frame-accurate-observable motion values, no damage/object-count change. Cited native: projectiles.rs:2434-2435, 2721-2727.

**Lion projectile homing Y-target offset sign inverted (aims 16px above player vs ROM 16px below)** (`loc_3E20E / loc_3E240 / loc_3E192`)
The shared homing block computes the Y target as `dy = (py - (0x10<<16)) - p.y_pos`, i.e. target = player_y − 16px, then adds +`homing_accel` (downward) when `dy>0`. The ASM `loc_3E20E` computes `d7 = y_pos(proj) - y_pos(kid) - $10` and branches `bmi loc_3E240` to add +$2000 when `d7<0`, so the convergence point is kid_y + $10 = 16px BELOW the player anchor. Native converges 32px higher than the ROM (16 above vs 16 below). The X axis is faithful (`loc_3E1C2`/`loc_3E1F4`). The Lion projectile is live: enemies.rs:19149 sets `homing_accel: 0x2000`. The native comment at projectiles.rs:2462 even states "Y homing target is 16px above player", directly contradicting the ASM math; the faithful port is `(py + (0x10<<16))`. Kind: deviating; live, player/TAS-observable hit/miss shift. Cited native: projectiles.rs:2462-2463, 2473.

**Native serializes skull startup to one pending worker; ASM allows concurrent `sub_86FA` workers within the 3-frame window** (`loc_A87A / loc_7718 / sub_86FA / sub_87B0`)
The 8-skull cap in ASM compares `cmpi.w #8,($FFFFFB70)` at C-press (loc_A87A:13167, loc_7718:7805), but `$FFFFFB70` is incremented only when `sub_87B0` actually starts — AFTER the 3-frame `sub_86FA` hibernate (`addq.w #1` at kid.asm:9626). Each C-press allocates an independent object slot running `sub_86FA`; nothing prevents multiple concurrent startup workers during the 3-frame window while `FB70<8` (the Juggernaut C path does not set the Kid's `is_animated`). Native models a single scalar `juggernaut_skull_delay_frames` and hard-blocks any new fire while it is `>0` (helmets.rs:6640), so only one startup can ever be pending. A TAS pressing C on consecutive frames queues several skulls in ASM but only one in native, and the effective cap timing during startup differs. Kind: deviating. A passing test (projectile_tests.rs:5525) pins the serialized behaviour and mislabels it ASM-faithful. Cited native: helmets.rs:6617, 6640, 6646.

**Spawn-in-solid immediate delete (`loc_899C`) not modelled at skull init** (`loc_87EC / sub_B55C / loc_899C`)
`sub_87B0` at spawn (after applying the ±$1A facing offset to x_pos) does `moveq #0,d7; moveq #0,d6; bsr.w sub_B55C; cmpi.w #$6000,d5; beq.w loc_899C` (kid.asm:9645-9649) BEFORE `Init_Animation`/first Hibernate. If the spawn cell is Solid, the skull goes straight to `loc_899C` and is deleted/exploded on frame 0 with no movement and no bounce-budget interplay. Native `juggernaut_skull_spawn_anchor_sub_87B0` only computes spawn x/y/x_vel; the comment at helmets.rs:478-481 admits this initial probe is "not modelled" and claims the per-frame solid check handles it implicitly. It does not: the per-frame check runs only AFTER moving by x_velocity (probing a different cell at Kid_x+26+4px vs the ASM's Kid_x+26px), consumes a `reaim`/bounce decrement instead of an instant delete, and the ASM gate fires on Solid only at offset (0,0) on the spawn cell. So a skull thrown into a wall (player hugging a wall facing it) instantly vanishes in the ROM but moves and bounces in native, changing which enemies it can hit and the object's lifetime. Kind: missing. Cited native: helmets.rs:469, 478.

**EyeClops beam does not reveal hidden blocks along its sweep (`sub_E446` path unwired)** (`loc_E70A / loc_E756 / loc_E790`)
In the ROM, `sub_E49A`'s render/collision tail (`loc_E70A` onward) computes the beam's block-column span and calls `sub_E446` (up to twice — the adjacent column at `loc_E790` once `($FFFFFAB8) >= 3`), which walks each column, finds `$7000`-mask `== $2000` HiddenBlock cells, resolves them via `sub_E37A`/`sub_E3C6`, writes the revealed cell back to the layout, and queues a `$12C`-frame foreground update plus `EraseBlockFromLevelLayout`. So the live EyeClops beam reveals hidden blocks across its horizontal sweep — an observable terrain effect. The faithful native port `hidden_block_column_updates_sub_E446` (terrain.rs:985, `duration_frames: 0x012C`) reveals exactly these cells but has only test callers (terrain.rs:4033/4082) and is `#[cfg_attr(not(test), allow(dead_code))]`; the whole `loc_E70A`/`loc_E756`/`loc_E790`/`loc_E79C` tail family in level.rs is likewise dead. The live `step_eyeclops_beam` (helmets.rs:6190) only pushes a point `EnemyProjectile` and never invokes any column scan, so beaming a wall of hidden blocks reveals nothing. Kind: helper-unwired. The helmets audit (#71) frames the beam tail as enemy damage and notes the render helpers are dead, but does not cite this hidden-block reveal channel. Tempered to medium as one facet of the known point-projectile root cause, gated on EyeClops + hidden blocks along the beam. Cited native: terrain.rs:985, terrain.rs:1019, helmets.rs:6190, lib.rs:3017.

**Lion projectile gets invented 120-frame DBF lifetime; ASM `loc_3E192` has none** (`loc_3E192 / loc_3E2A8 / sub_3E2CE`)
The Lion homing-roar child is spawned with `lifetime: 120` (enemies.rs:19145) and its kind is NOT in the projectile lifetime-exemption list (projectiles.rs:2387-2393), so the live `retain_mut` loop decrements `p.lifetime` each frame and deletes it at 0. The ASM loop `loc_3E192` (and bounce loop `loc_3E2A8`/`loc_3E2C0`) has NO frame-count/DBF lifetime: the projectile survives until terrain/object collision or until `sub_3E2CE` finds it outside the camera box (or its parent token mismatches); the `dbf d0,loc_3E2A8` is an inner bounce-resolution loop (d0=$F), not a per-frame lifetime. In an open arena where the homing projectile stays inside the camera box and hits no terrain, native force-deletes it after 120 frames (~2s) while the ROM keeps it alive and homing. Kind: deviating; observable motion/lifecycle divergence in a narrow but real window. Cited native: enemies.rs:19145, projectiles.rs:2387-2415, 2890-2901.

### Low severity

**Faithful `probe_relative_collision_sub_B55C` exists but skull live path uses broad `solid_terrain_at`** (`sub_B55C / loc_8852 / loc_8916`)
terrain.rs:1665 has a faithful port returning the exact `CollisionKind` (so a caller could gate on `== Solid` like the ASM's `cmpi.w #$6000`). It is live-wired in movement.rs (4537/7639/7985/8004/8087/8097) and helmets.rs:322, but the skull step (projectiles.rs:2014/2059) calls the invented `solid_terrain_at` broad `!= Empty` substitute. Kind: helper-unwired; standalone wiring note — the observable damage is captured by the high-severity skull terrain gap above. The test at projectile_tests.rs:6541 wrongly asserts `solid_terrain_at` "mirrors that gate" but only exercises the `has_block` + `collision=Empty` presentation case.

**Juggernaut skull gets invented 120-frame DBF lifetime; ASM `sub_87B0` has none** (`sub_87B0 / loc_8810 / loc_899C`)
The friendly skull is spawned with `lifetime: JUGGERNAUT_SKULL_LIFETIME` (=120, constants.rs:729) and kind Generic, not in the lifetime-exemption list, so the live `retain_mut` loop force-deletes it after 120 frames before the skull early-returns through `step_juggernaut_skull_sub_87B0` (projectiles.rs:2489). ASM `sub_87B0`/`loc_8810` has no frame timer and no camera box: it deletes only on level collision (`tst.b $19(a3)`), object collision (`tst.w collision_type`), or exhausting its 4-bounce counter. A skull thrown over open space/a pit (no terrain contact, no bounce) lives indefinitely in the ROM but dies at 120 frames natively. Kind: deviating. Cited native: helmets.rs:6630, projectiles.rs:2387-2415, 2489-2491.

**`sub_3E2CE` parent-token gate not enforced on the live cull path; faithful helpers are dead** (`sub_3E2CE / loc_3E30E / loc_3E314`)
ASM `sub_3E2CE` first compares the projectile's owner token (`move.b $71(a5),d6 / cmp.b $71(a0),d6 / bne loc_3E314`) and deletes the projectile (decrementing the owner's active count at `loc_3E30E`) when the owning Lion's token no longer matches, BEFORE the camera-box check. The live generic owner-box cull (projectiles.rs:2890-2901) only tests `p.owner.is_some()` and the camera box; it never re-checks the token against the live enemy, so a projectile whose parent was despawned/replaced (slot/token reused) is not self-deleted as in the ROM. The two faithful helpers `lion_projectile_owner_token_mismatch_loc_3e30e` (projectiles.rs:3163) and `lion_projectile_screen_range_delete_loc_3e314` (projectiles.rs:3170) carry `#[cfg_attr(not(test), allow(dead_code))]` and have no production caller. `release_lion_projectile_owners` (projectiles.rs:2083) only validates the token when decrementing the count AFTER deletion, not to trigger the token-mismatch deletion. Kind: helper-unwired.
