# Level-Flow & Timer Fidelity Audit

Adversarially-verified per-unit audit of the Kid Chameleon source-port level-flow, timer, death and end-of-level subsystems. The dominant failure pattern is the codebase-wide "faithful-but-untranslated normalisation": the ROM keeps several state variables in a deliberately pre-compensated form (the `addq #1,(Time_Seconds_low_digit)` + `SubSeconds=1` timer normalisation at level start and at each clock collect; the `clr.w (Extra_hitpoint_slots)` that `lose_life` performs before reseeding HP; the MapOrder reverse/forward index translation), and the native port either drops the compensating step or substitutes a structurally simpler model. The timer normalisation is now fixed-candidate, but the same pattern remains elsewhere: extra-HP slots survive a death the ROM would wipe, and the final-level/teleporter level-id decisions read the wrong index. The extra-HP carry remains entrenched by regression tests that pin the *deviating* native values, so it would not surface without an oracle/disassembly cross-check.

## Confirmed gaps

### High severity

**Death respawn never clears `Extra_hitpoint_slots`; native retains DP extra-HP slots across death, over-restoring max HP** (`lose_life` / `Death` / `Init_Timer_and_Bonus_Flags`; reported by units respawn-state-persistence-reset, death-respawn-lifecycle-state-machine and death-cause-routing-and-windup-entry)
The ROM's `lose_life` makes `clr.w (Extra_hitpoint_slots).w` (kid.asm:14764) its very first action, *before* `move.w #2,(Number_Hitpoints).w` (kid.asm:14768), so every same-level death respawn drops the player back to the base TheKid HP cap of 2; the `Death` routine also zeroes the field on entry (kid.asm:14719). Native's death entry `enter_death_hidden_state` (combat.rs:9841-9852) sets `current_form=TheKid`, `number_hitpoints=2` and decrements lives, and `reset_current_level_runtime_state_for_respawn` (level.rs:17927-17996) wipes enemies/platforms/projectiles/diamond-power slots/timer/clocks, but **neither touches `progression.extra_hitpoint_slots`** — the only live writer of that field is the ExtraHitPoint diamond-power increment (helmets.rs:4805, reached each Alive frame via lib.rs:2097 → `step_diamond_power` → `step_diamond_power_extra_hp_life_slots_loc_3fbe4`). The stale slots are then read by the HP-cap recompute (combat.rs:9259-9263, lib.rs:2963) and the transform restore `transform_hitpoints_sub_7eb2` (combat.rs:9067), so a player who collects an ExtraHitPoint power, dies and respawns keeps an inflated HP cap (e.g. RedStealth restoring 3+slots instead of the ROM's 3+0) and saturates the four-slot ceiling (helmets.rs:4102) earlier than the ROM. The prior tracking entry rates this "Hygiene until the field is populated" on the now-false premise that the field is inert; the 2026-05-31 ExtraHitPoint DP fix made it live, so the gap is realised and player-observable. Kind: missing reset on the in-scope respawn path.

**Final-level ending trigger fires at the last MapOrder entry (logical `$69`) instead of the hard-coded `Final_LevelID=$33`** (`loc_D7F4` / `End_Credits` / `Final_LevelID` / `Boss4_LevelID`; reported by units level-complete-to-next-level-exit-routing and final-boss-ending-trigger-and-bonus-entry)
The ROM EOL routine routes the ending with an exact compare: `cmpi.w #Final_LevelID,(Current_LevelID).w; beq.w End_Credits` else `addq.w #1,(Current_LevelID).w; bra.w Teleport` (kid.asm:16912-16917), where `Final_LevelID = $33` (kid.asm:30) `== Boss4_LevelID = $33` (kid.asm:47). `Current_LevelID` is the *logical* MapOrder index (proven by `Get_PlatformLayoutAddress`, kid.asm:4194-4196), so the ending fires only when the logical index reaches `$33`. Native `is_final_level()` instead returns `logical_level_ids().last() == current_level` (level.rs:18032-18037); the shipped `maporder.asm` has non-`$FF` entries through logical `$69` (first terminator at index `$6A`), so the native "last level" is `LevelId($69)`, not `$33`. `advance_level()` (reached live from the LevelComplete countdown at boot.rs:7730-7744) therefore never enters `BootState::EndingSequence`/`game_complete` when the player completes Plethora (`$33`); it falls through to `next_level_id()` and keeps routing through ~50 extra logical levels, never ending at the true final level. The `+1` linear advance itself is faithful (no interior `$FF` holes), and the dead helper `is_boss_level_loc_C03A` (boot.rs:756-758) already encodes `$33` as Boss4 — so the correct port is a literal `current_level == LevelId(0x33)` check. The unit test (combat_tests.rs:15181) uses a synthetic 3-entry map_order where `last==final`, masking the real ROM mismatch. Kind: deviating.

**Live teleporter path skips the `loc_BCD6` MapOrder reverse scan: `dest_map_id` (a map number) is used directly as a logical level index** (`loc_BCB2` / `loc_BCD6` / `loc_BCEA` / `Get_PlatformLayoutAddress`)
The ASM telepad record's high byte at `+6` is a *map number*, not a logical index. `loc_BCB2` extracts it (`move.w (a4),d7; asr.w #8,d7`), then `loc_BCD6` scans `LnkTo_MapOrder_Index` byte-by-byte so that `d6` becomes the *logical index* whose MapOrder entry equals that map number; `loc_BCEA` compares `d6` (the index) to `Current_LevelID` and stores `d6` back — the exact inverse of `Get_PlatformLayoutAddress` (kid.asm:4194-4196). Native's live path (combat.rs:10999-11012) instead does `if dest_map == self.current_level.0` (comparing a raw map number against a logical index) and `pending_level_skip = Some(LevelId(dest_map))` / inline reposition keyed on `dest_map`, with **no reverse scan anywhere in `crates/kid-core/src/`**. Because `map_order` is a non-identity permutation (kid-data confirms `map_order[9]=0x56`; the shipped fixture maps index 0→`$4A`, 2→`$2D`, …), a cross-level telepad will both mis-classify same-vs-cross-level and warp to the wrong logical level (`LevelId(map_number)` rather than the index that maps to it) — an authoritative warp-destination error. The combat.rs:10992 comment claims the scan is "implicit"; given the non-identity permutation that assertion is itself the bug, and the regression test (projectile_tests.rs:2202) pins the scan-skipped behaviour. Field extraction (terrain.rs:764-774) and the `dest_x<<20`/`dest_y<<20` scaling are faithful; only the index translation is missing. Kind: missing. Native locations: combat.rs:10999-11012, combat.rs:9044-9047, terrain.rs:764-774, level.rs:14157 + kid-data/src/lib.rs:1071-1085.

### Medium severity

**RESOLVED candidate — level timer starts with the ROM's 181s pre-decrement budget** (`Init_Timer_and_Bonus_Flags` / `Init_SpriteAttr_HUD` / `loc_BE82`)
On level entry the ROM sets minutes=3/seconds=0 in `Init_Timer_and_Bonus_Flags` (kid.asm:6555-6561), then `Init_SpriteAttr_HUD` does `addq.w #1,(Time_Seconds_low_digit)` (kid.asm:27099) **and** `move.w #1,(Time_SubSeconds)` (27100). The true start state is therefore 3:01 with `SubSeconds=1`; the first gameplay frame drains `SubSeconds 1→0`, reloads `$3C`(60) and decrements 3:01→3:00 (kid.asm:15482-15485). Native now seeds `LevelTimer::new()` at 181 seconds with `sub_frames=1`, preserving the same first-frame normalisation and one-second-longer death budget. The EOL completion-time path deliberately uses a separate `LEVEL_TIMER_COMPLETION_BASE_SECONDS=180` because `loc_C0CC` subtracts remaining time from literal `$B4` and adds `Clocks_collected*$B4`. Kind: fixed-candidate. Native locations: types.rs, constants.rs, combat.rs, trace.rs.

**RESOLVED candidate — clock-bonus now applies the `loc_FF92` `+1`-second carry before `loc_FFDE` adds three minutes** (`loc_FFDE` / `loc_FFFC` / `loc_10002`)
The ROM clock-collect tail, immediately before the `+3`-minute add, does `addq.w #1,(Time_Seconds_low_digit)` with full BCD carry into seconds-high/minutes (kid.asm:21271-21279), then `loc_FFDE` adds 3 to `Time_Minutes` capped at 10:00 (21282-21293), then `loc_FFFC` sets `Time_SubSeconds=1` (21296). Native `add_clock_bonus` now adds `LEVEL_TIMER_CLOCK_COLLECT_SECONDS=181` and caps to 10:00, while the EOL speed-bonus elapsed formula still multiplies `Clocks_collected` by the ROM's flat `$B4`. Regressions cover the clean +3:00 after the compensating tick and the 6:59→10:00 cap boundary. Kind: fixed-candidate. Native locations: types.rs, constants.rs, combat.rs, trace.rs.

**RESOLVED candidate — Continue (CONTINUE?) screen accepts Start only and preserves the second Start window** (`loc_D350` / `loc_D3AA` / `Use_Continue` / `Continue_Screen`)
On the CONTINUE? screen the ROM polls `Ctrl_Held` and branches to `Use_Continue` only when the Start bit is held: `tst.b (Ctrl_Held).w; bmi.s Use_Continue` (kid.asm:16528-16532, identically at 16555-16559); `Button_Start=7` so `tst.b`+`bmi` tests bit 7 alone. Native gates the live `ContinueCountdown` use path on `input.start`, has a regression asserting A/B/C alone leave the countdown running, and includes the post-fade `$EF` `loc_D3AA` Start window before title return. Reachable in normal play via GameOver → ContinueCountdown when `number_continues>0`. Kind: fixed-candidate.

**GameOver arm injects a 2P player-switch the ASM zero-lives path never performs** (`loc_D052` / `loc_D17E` / `loc_D25E` / `loc_D2CE` / `loc_D3F0` / `Use_Continue`)
When the current player's `Number_Lives` reaches 0 the ROM always takes `beq.w loc_D052` (game-over teardown), even in two-player: `loc_D17E` merely allocates the P1/P2 indicator text objects then falls into the *same* `loc_D25E` continue/title decision, reaching `loc_D3F0` (`clr.w (Game_Mode)` → title) when no continues remain (kid.asm:16325-16601). The surviving-player handoff (`loc_B894`/`loc_B8D0`/`not.b Current_player`) lives only on the **non-zero-lives** `Teleport` path, so the ROM abandons a surviving player's saved lives when the current player games over with no continues. Native's GameOver arm adds `else if self.try_switch_player() { Alive }` before `return_to_title()` (boot.rs:7769-7773; level.rs:18327-18341 swaps to the surviving player), an invented recovery branch reachable in live 2P. Two native tests (`two_player_game_over_switches_when_other_has_lives`, `loc_b8d0_p1_dead_p2_alive_forces_p2_active`) pin and entrench this behaviour. Kind: deviating. Note: there is a *second*, faithful `try_switch_player()` call in the `Dying` arm (boot.rs:7656) guarded by `number_lives != 0` — only the 7769 GameOver-arm site is the gap.

**FC36-set respawn/continue/cross-level-teleport paths clear NoPrize but never clear the NoHit bonus flag (`level_damage_taken`)** (`Init_Timer_and_Bonus_Flags` / `lose_life` / `Use_Continue` / `loc_BCEA`)
When `$FFFFFC36` is set, `Init_Timer_and_Bonus_Flags` reloads the timer **and** clears *both* bonus flags: `sf (NoHit_Bonus_Flag); sf (NoPrize_Bonus_Flag)` (kid.asm:6559-6560). Every native FC36-set path resets the NoPrize analog (`level_prize_collected=false`) but never the NoHit analog `level_damage_taken`, which is set true at combat.rs:9253 (on damage) and consumed at combat.rs:7558 to award the level-complete NoHit 5000-point bonus. The death-respawn + continue path `reset_current_level_runtime_state_for_respawn` (level.rs:17927/17974; callers boot.rs:7661 death, boot.rs:7793 Use_Continue — FC36-set at kid.asm:14770/16574) and the cross-level-teleporter resume `maybe_begin_pending_level_skip_resume` (boot.rs:7492/7520, FC36-set at kid.asm:15273) clear `level_prize_collected` but leave `level_damage_taken` carrying its prior-life true value. Observable consequence: a player who takes damage, then dies or uses a continue mid-level, then completes the level cleanly has the 5000-point NoHit bonus incorrectly withheld. The consequence is score-only, but the auditor for this unit (respawn-state-persistence-reset) and the FC36-gate unit both flag it as a real omission of the FC36 gate's bonus-flag semantics; the refuter corrected severity from the low default to medium given the authoritative bonus-denial. Kind: missing. Native locations: level.rs:17927, level.rs:17974, boot.rs:7492, boot.rs:7520, combat.rs:9253, combat.rs:7558.

### Low severity

**Native grants 66-frame post-respawn invuln after *every* death; the ROM only grants it when the kill latched `Just_received_damage`** (`Check_for_recent_damge` / `loc_B72C` / `loc_BC40` / `Crushed_to_Death` / `loc_9142`)
In the ROM, post-damage invulnerability is the latched `Just_received_damage` byte (`$FFFFFA73`): `Check_for_recent_damge` (kid.asm:14633) skips all damage while it is set, and the cosmetic flash thread clears it only after its 66-frame cycle (kid.asm:15214). It is `st`-set **only** by depleting contact/projectile damage at `loc_B72C` (kid.asm:14657); `lose_life`/`Teleport`/`loc_6E2`/`Load_InGame` never write it. The two non-damage death entries — `Crushed_to_Death` (kid.asm:14571, murder wall) and `loc_9142` (kid.asm:10549-10552, pit fall) — branch to `Death` without setting it, so on those respawns the Kid is immediately vulnerable. Native unconditionally seeds `invulnerable_frames = PLAYER_DAMAGE_INVULNERABLE_FRAMES` (66) at the end of the Respawning arm (boot.rs:7696-7700) for all causes, after clearing `just_received_damage` at the respawn reset (level.rs:17987-17988). Low because respawn lands at level start where immediate re-damage is rare, but it is an authoritative damage-immunity difference. Kind: deviating.

**Death entry does not clear `Extra_hitpoint_slots`, retaining DP extra-HP slots across death/respawn** (`Death` / `lose_life`)
Reported by the death-cause-routing unit as the same root as the high-severity carry above (the `Death` routine zeroes the field at kid.asm:14719 and `lose_life` again at kid.asm:14764; native `begin_death_windup_path` at combat.rs:9320 and `enter_death_hidden_state` at combat.rs:9841 never touch `progression.extra_hitpoint_slots`). Merged into the high-severity entry; retained here only to record the death-cause unit's independent corroboration. Kind: missing.

**`resolve_frame_hazards` checks level-timer death before pit-fall; the ROM defers timer death one frame, so a coincident fall picks the wrong windup path** (`loc_9142` / `Crushed_to_Death` / `Character_CheckCollision`)
Native `resolve_frame_hazards` (combat.rs:10907-10926) evaluates the level timer (`begin_death_windup` = Tumble) before `fell_below_level` (`begin_pit_death_windup` = PitFall) within the same frame. In the ROM the timer-out does not branch to `Death` directly — `Decrease_Time_Left` writes `move.w #4,collision_type(a3)` (colid_rightwall), consumed only by the *next* frame's `Character_CheckCollision` → `Crushed_to_Death` → `moveq #0,d7` Tumble (kid.asm:15494-15499, 14571). The pit kill (`sub_902A` `loc_9142`) fires immediately in the same frame's floor probe with `d7=1` (PitFall, kid.asm:10454/10550). So if the timer hits zero on the same frame the player crosses below `Level_height_pixels`, the ROM produces a PitFall windup while native produces a LevelTimerDeath Tumble — different path and mutator tag. Rare coincidence; both are deaths. Kind: deviating.

**`fell_below_level` fires regardless of y-velocity direction; the ROM pit kill is only reachable from the downward floor-probe branch** (`sub_902A` / `loc_9142` / `loc_908C`)
Native `fell_below_level` (combat.rs:8952-8956) returns true whenever `(y_pos>>16) >= height_pixels`, unconditionally. In `sub_902A` the `Level_height_pixels` compare that reaches `loc_9142` (pit death, `d7=1`) lives only in the *downward* branch (entered when `y_vel >= 0`, i.e. the `bmi loc_908C` is not taken); the upward branch `loc_908C` has no `Level_height_pixels` check, so the ROM never triggers a pit death while the player is moving up even if the new top-pixel y is at/below the boundary (kid.asm:10440-10441, 10453-10455, 10476-). Native would mis-trigger PitDeath in that upward-below-floor case. Practically near-unreachable (you are below the floor only while falling). Kind: deviating.

**GameOver hold runs the full 419-frame timer before the continue decision; the ASM reaches the continue screen in ~34 frames when continues remain** (`loc_D0C0` / `loc_D15E` / `loc_D25E` / `Continue_Screen` / `loc_D2CE`)
The ROM runs only a short shared fade tail before the continue decision: `loc_D0C0` hibernates one frame and `loc_D15E` decrements `$FFFFF876` from `$100` by `$10` until it equals `$70` (~9 iterations) before `loc_D17E` → `loc_D25E` (kid.asm:16368, 16416-16420, 16472); the `$1A3` (419) frame wait at `loc_D2CE` belongs only to the no-continues path. Native applies `PLAYER_GAME_OVER_HOLD_FRAMES=419` unconditionally (`if remaining_frames > 1`) before deciding continue-vs-title (boot.rs:7760-7768, constants.rs:508), so when continues remain the player waits ~419 frames before the interactive continue screen rather than ~34. The continue-vs-title routing itself is correct; only the hold ordering/duration deviates. Adjacent to the excluded continue/game-over screen (shell) scope. Kind: deviating.

**`sub_B43A` WarpCheat dest-level override branch absent from the native floor probe** (`sub_B43A` / `loc_B482` / `WarpCheatStart_LevelID` / `WarpCheatDest_LevelID`)
`sub_B43A`'s entry preamble (kid.asm:14352-14364) implements a developer warp cheat: when `Character_Movement == MoveID_Crawling`, the level is `WarpCheatStart_LevelID` (1), the Kid is at exact pixel `x=$09D3,y=$005F`, and Button_B is held, it writes `move.w #WarpCheatDest_LevelID,(Current_LevelID).w` (`$32`), sets `collision_type=colid_kidbelow` and `object_meta=$A0`. This is the only non-HundredKTrip secret level-destination routing path in the engine. The native port `walking_floor_support_exists_at_current_position` (movement.rs:5664, live-called at 2858/3115/4217/4234) is faithful from `loc_B4A0` onward but entirely omits the crawling-check + warp-cheat block; no `Current_LevelID` override exists in `movement.rs`. Low: a cheat reachable only via held B at one exact crawl position, no effect in normal play — flagged because the unit asked whether *any* native non-100K secret routing path exists; it does not. Kind: missing.
